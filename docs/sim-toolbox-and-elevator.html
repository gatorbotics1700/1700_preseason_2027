Part 1 - PR Sim Toolbox - branch sim-framework

The toolbox

It runs the whole robot in the simulator by itself, reads the log, and tells you what went wrong. The same checks also read a log from a real match.

What was there, and what was added on top

  • The checks live in the test folder, not on the robot. They read log files. They never run in the 20 ms loop, so they cannot slow the robot down.
  • SimSmoke is in the robot code because it has to run inside the robot program, to pick the auto and press enable. It only wakes up when a smoke test asks for it.

What happens in a smoke test

  1. StartGradle starts the simulator with no window.
  2. Hook inRobot.java builds SimSmoke and also writes a log file.
  3. Pick the autoAfter 1 s, SimSmoke picks the auto on the dashboard, like a driver.
  4. EnableIt enables autonomous. Every loop is logged.
  5. FinishThe auto ends. It closes the log and exits.
  6. CheckLogDiagnostics runs every check and prints PASS or FAIL.

Waiting is counted in robot loops, not clock time. If the auto never starts or never ends, it gives up and fails.

The classes inside the log checks

A check lists the log keys it needs. If the log does not have them, the report says SKIP, not FAIL. That is how one list of checks works on every log.

Part 2 - PR Elevator Prototype - branch elevator-prototype

The elevator

One mechanism built the new way from start to finish, as the example the other mechanisms copy. No robot has an elevator yet, so it is switched off on the real robot.

The mechanism pattern, and how the elevator fills it in

The elevator is a brand-new mechanism. It does not replace anything. It follows a pattern that was already on main, and adds the pieces the toolbox made possible. Step through the three tabs to watch the same picture grow.

Which version runs where

Real robotElevatorIOTalonFX

When ENABLED_ON_REAL_ROBOT is true. Today it is false, so the robot gets the do-nothing version.

Simulator and smoke testElevatorIOSimPhysics

Real motor code, with a physics model answering for the motor and the switch.

Unit testsElevatorIOSim

The test sets every reading itself, so tests run instantly.

Off, or replaying a lognew ElevatorIO() {}

Every method does nothing. No fake CAN ID needed.

RobotContainer picks one when the robot starts. The day a robot has an elevator: put the real CAN ID and DIO port in the config file, replace the guessed numbers with measured ones, and set ENABLED_ON_REAL_ROBOT = true. No class changes.

Inside: the same code, a different thing answering

What the elevator does

Not homedhome → Homingswitch pressed → Homedgo to a height → Movingwithin 1 cm → At goal
Alert on the Driver StationWhen
Motor disconnectedthe motor stops answering
Homing failed4 s (200 loops) with no switch press
Told to move but not there2 s (100 loops) away from the goal

It will not move to a height until it is homed. Going to the bottom, it slows to a gentle push and then turns the motor off, so it does not hold current against the hard stop.

Two things to check on the first CAD export. First, the size tests read the raw size of the shapes in a file and ignore any move or turn stored inside it, so compare one size by hand before trusting them. Second, export each moving part with the elevator all the way down, because a logged pose means "how far this part has risen".

One set of numbers, used everywhere

ElevatorConstants types every number once. The real motor settings, the physics model, the 3D boxes and the log checks all read from it. Change a travel limit once and all four follow. Most of the numbers are guesses today, marked TUNED, NOT DERIVED, until the build team measures a real elevator.
